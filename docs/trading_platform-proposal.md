# Предложение в trading_platform: индексы для инкрементального чтения

Текст для issue/PR в `geo-info/trading_platform`. cadastre-etl сам в trading_platform
не пишет.

## Что делает cadastre-etl

Раз в `INTERVAL` (30 минут) по каждой коллекции площадки выбирает лоты, изменившиеся
после прошлой проверки:

```js
{"$or": [{"updated_at": {"$gt": since}}, {"detail_at": {"$gt": since}}]}
```

Индексов по этим полям сейчас нет — каждый прогон читает каждую коллекцию целиком.

## 1. Индексы по `updated_at` и `detail_at`

В `MongoStorage.__aenter__`, рядом с уникальным индексом по ключу:

```python
await self.collection.create_index([("updated_at", 1)])
await self.collection.create_index([("detail_at", 1)])
```

`$or` по двум индексированным полям Mongo выполняет двумя сканами индекса вместо
полного просмотра коллекции. `pending_detail` индексы не помешают (он сравнивает поля
между собой через `$expr` и индексом по ним всё равно не пользуется).

## 2. (по желанию) Время записи деталей

`save_detail(lot_id, detail, at)` пишет `detail_at = at` — время *запроса* страницы,
чтобы лот перечитался, если листинг обновил его во время запроса. Для внешнего
читателя это значит: документ появляется с `detail_at`, отстающим от момента записи
на длительность запроса (до `HTTP_TIMEOUT` и повторов). Поэтому cadastre-etl держит
перекрытие окна в 10 минут.

Если писать рядом `detail_saved_at = now()` (и индекс по нему), cadastre-etl сможет
выбирать по нему и сократить перекрытие до минуты. Смысл `detail_at` не меняется.
